🛒 Kiran Bazaar: Project Explainer

CT-378 Machine Learning · plain-language guide to what the project does, for the group and the viva
In one sentence: given a city (Karachi, Lahore, Multan, Peshawar, Quetta) and a food staple (atta, rice, sugar, oil, ghee, milk, eggs, chicken, daals), the system predicts the probability that its price will rise by more than 5 % next month, e.g. "Wheat flour (atta) in Lahore: 23 % chance of a >5 % jump in November 2026".

1. What problem are we solving? Classification or regression?

Main task = binary CLASSIFICATION. For every city + staple + month, the answer is Yes (spike) or No (no spike):

  • Spike = 1 if next month's price is more than 5 % higher than this month's price; otherwise 0.
  • The model outputs a probability (0-100 %). If it is above 22% (our tuned alert threshold), the app says "spike likely".

Extra task = REGRESSION (a smaller side model): predict the expected % change in price, which the app turns into "expected price next month: Rs 111.9".

Why classification as the main task? Month-to-month price changes are close to random, so predicting the exact number is very hard (our regression only barely beats "no change"). Predicting the event users care about ("will it jump?") is learnable and gives clean metrics (F1, ROC-AUC). It also differs from the published work on this dataset, which used regression.

3. How the raw data becomes a training table

  • Each row = one city × one staple × one month, e.g. "Lahore, Sugar, March 2023".
  • Time window used: Jan 2014 to Sep 2026 (before 2014 only rice and wheat were recorded, and fuel/wage data did not exist). Result: 9,633 labelled rows; ~15 % of them are spikes. The newest month (Oct 2026) has no answer yet; it is the month the app forecasts from.
  • 26 input features, all computed using only the current and past months (never the future), plus 5 more created inside the pipeline:

4. How we trained and tested (the ML lifecycle)

  1. EDA (notebooks/01_eda.ipynb): 7 plots covering data coverage/missing values, distributions, price vs rupee trend, outliers, class balance, correlations, seasonality.
  2. Pre-processing inside a scikit-learn Pipeline: fill missing values (median, plus missing-value flags) → scale numbers (StandardScaler) → one-hot encode text columns. Fitted on training data only, so there is no data leakage.
  3. Time-ordered split (70/15/15): train = 2014-01 to 2022-12 (6,711 rows) · validation = 2023-01 to 2024-10 (1,427) · test = 2024-11 to 2026-09 (1,495). We never train on the future and test on the past.
  4. Tuning: GridSearchCV / RandomizedSearchCV with 5-fold time-series cross-validation, optimising ROC-AUC.
  5. Model selection on validation → best model picked → probability calibration → alert threshold tuned for best F1 → retrained on train+validation → tested once on the test set.
  6. Saved with joblib in models/; versions pinned in requirements.txt.

Final deployed model = Random Forest (300 decision trees, max depth 16, at least 25 rows per leaf, √features tried at each split), plus probability calibration. It had the best validation ROC-AUC (0.751), essentially tied with Bagging (0.750). Both are ensembles of decision trees; we followed our fixed rule "highest validation ROC-AUC wins". Averaging many trees reduces the over-fitting a single tree suffers from.

Why calibration?

The forest uses class_weight="balanced_subsample" so that it pays attention to the rare spikes. Side effect: its probabilities came out too high. On validation it predicted a 44% average spike chance when the real rate was 18%, so the app would have said "59 % chance" for atta when the truth is nearer 20 %. We wrapped the model in CalibratedClassifierCV (sigmoid / Platt scaling), which learns a mapping from raw scores to real-world frequencies. On validation the average prediction became 18%, and the Brier score (probability error, lower is better) fell from 0.204 to 0.132.

How to read it: if the model says "30 %", then about 30 % of those months should really spike, so a perfect model sits on the dashed diagonal. The red line (before) lies far below it: the model was over-confident. The blue line (after) follows it closely.

Unsupervised algorithms (notebook 03, analysis only)

  • PCA: 10 components keep 90 % of the information; the first component is a "price momentum" direction.
  • K-Means (k = 4): groups the 65 city-item series into volatile perishables (chicken, eggs), rupee-sensitive items (daals, rice, wheat), rare-jump items (ghee, oil) and stable items (milk, sugar).
  • Apriori: finds items that spike together. Ghee ↔ cooking oil (lift ≈ 7, both use imported palm oil), the three daals, and wheat ↔ atta.

Reading the confusion matrix

  • 127 spikes correctly predicted (true positives)
  • 64 spikes missed (false negatives)
  • 210 false alarms (false positives)
  • 1094 calm months correctly predicted (true negatives)
Why we don't lead with accuracy: only ~13 % of test months are spikes, so a useless model that always says "no spike" would score ~87 % accuracy. That's why the guideline asks for F1 / ROC-AUC / confusion matrix, and why we report those.

Is it good enough? Yes for the project. The guidelines mark the quality of the lifecycle, not a minimum score. The model clearly beats both baselines (ROC-AUC 0.83 vs 0.61; F1 0.48 vs 0.33). Food prices one month ahead are partly random, so 0.83 is a solid result. We set the alert threshold to 22% (not 50 %) on purpose: for an early-warning tool it is better to catch most spikes and accept some false alarms.

Regression on test: MAE 3.46 percentage points vs 3.56 for "no change", R² 0.05. That is only a small improvement, which confirms that classification was the right main framing.

7. Over-fitting / under-fitting

Train vs validation ROC-AUC
  • Over-fitting: KNN (train 1.00 → val 0.70) memorises the training data; Gradient Boosting (0.96 → 0.74) also over-fits.
  • Under-fitting: Logistic Regression and Naive Bayes have small gaps but low scores; they are too simple for the non-linear pattern.
  • Random Forest and Bagging (both 0.93 → 0.75) give the best validation scores. They still over-fit somewhat, which min_samples_leaf=25 and max_depth=16 limit.
  • Validation (2023-01 to 2024-10) has more spikes than training (18 % vs 15 %, the tail of the 2022-24 inflation shock), which makes it harder.

9. Limitations (be ready to say these yourselves)

  1. Only 5 big cities and monthly data. Small towns and weekly movements are not covered.
  2. Uneven skill across items: good for moong daal, cooking oil, sugar, milk and wheat; close to random for eggs, basmati rice and mash daal (masoor daal's high score rests on a single test spike). Part of the overall 0.83 comes from simply telling volatile items from stable ones.
  3. No shock information: floods, government wheat support-price announcements, import bans, bird flu and Ramadan/Eid timing are not in the features.
  4. Regime shifts: the spike rate changes over time (15 % train → 18 % validation → 13 % test), so even calibrated probabilities can drift; the model should be retrained (and re-calibrated) regularly.
  5. Fuel / exchange-rate features were untested in a devaluation period inside the test window.
  6. Regression is weak (R² ≈ 0.05): the "expected price" is a rough guide only.
  7. Data is secondary (collected by PBS/WFP), so we inherit any recording errors and gaps (40-50 % of months are missing for items that start in 2013-15).

Future work: add weekly PBS SPI data and more cities, international wheat and palm-oil prices, a calendar of Eid/Ramadan and policy events, per-item models, and probability calibration.

12. Likely viva questions and short answers

Q: Is this classification or regression?
Classification (spike yes/no, >5 % rise next month). A small regression model gives the expected price as an extra.

Q: Why 5 %?
It marks a real jump that hurts households, yet happens often enough to learn from (~15 % of months). At 10 % only ~4 % of months would be positive.

Q: Why not a random train/test split?
Neighbouring months are almost identical, so a random split leaks future information into training. We split by time and use TimeSeriesSplit for cross-validation.

Q: How did you avoid data leakage?
(1) Features use only current and past months. (2) All pre-processing sits inside the Pipeline, fitted on training data only. (3) Time-ordered split. (4) The test set was used exactly once.

Q: Why is accuracy 82% but you say F1 0.48?
The classes are imbalanced (≈13 % spikes in test), so accuracy is misleading. F1 and ROC-AUC measure performance on the rare spike class.

Q: Why Random Forest and not Bagging?
They were essentially tied on validation ROC-AUC (0.751 vs 0.750). We fixed the rule "highest validation ROC-AUC wins" in advance and followed it. We selected on validation, not on test. Random Forest also tries a random subset of features at every split, which makes its trees more diverse.

Q: Why did you calibrate the probabilities?
Class weighting made the raw forest over-confident: average prediction 44% vs a real spike rate of 18% on validation. Platt scaling (CalibratedClassifierCV) fixed this (18%), so "23 % chance" in the app really means about 23 %.

Q: Why is the threshold 22% and not 50 %?
With only ~15 % spikes, a calibrated probability rarely reaches 50 %, so a 0.5 cut-off would miss most spikes. We chose the threshold that maximised F1 on the calibrated validation probabilities. A 22% chance is already well above the normal ~13 % spike rate.

Q: How did you handle class imbalance?
class_weight="balanced", tuning on ROC-AUC instead of accuracy, the F1-optimal threshold, and calibration so probabilities stay honest.

Q: What was your biggest mistake and how did you fix it?
The first version used price and exchange-rate levels. These rise for 20 years, so models had to extrapolate (Logistic Regression val ROC-AUC 0.51). Switching to % changes raised it to 0.71.

Q: What are the two data sources?
WFP food prices (with fuel, wage and implied USD/PKR series) and the WFP markets table, both from HDX under CC BY-IGO.

Q: What do PCA, K-Means and Apriori add?
PCA shows the signal is spread over ~10 directions; K-Means groups items by price behaviour; Apriori shows which items spike together (ghee and oil, wheat and atta).
